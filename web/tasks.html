八个任务

八个任务共用同一套机器人、控制器、观测和策略接口，但它们并不是同一种东西 —— 只有其中五个真正把「必须靠力才能判断」写进了任务设定。这个区别在本站任何地方都不会被抹掉。

任务卡片尚未成文

逐任务的正式文档卡片还没写（仓库 CHANGELOG.md 中作为 v1.0 待办跟踪）。 在那之前，任务的权威定义是仓库里 forcebench/tasks/<name>/ 下的 spec.py 与 runtime.py；本页只是面向读者的概览。

◆力分类任务（5 个）

这五个任务里，决定「怎样做才算对」的那个物体属性在视觉上完全不可观测： 箱子外观一模一样但轻重不同，包裹总质量固定但配重位置不同，旋钮/手柄的卡位只有力矩才能感知， 抽屉的起拉阻力也只能拉了才知道。力是唯一携带这些信息的通道 —— 策略要么用力，要么只能靠猜。

■接触密集任务（3 个）

这三个任务接触丰富，作为操作任务本身是有意义的，但必须如实说明：

⚠ 当前判分并不检验力感知

截至 v0.1，这三个任务的成功判定只检查最终位姿（是否居中/就位/对齐/松开/退回）， 从不读取 wrench 信号；peg_insert 的 spec 里甚至完全没有力或质量相关的常量。 它们的 MANIFEST 描述里写着 "force-sensitive"，但这个措辞是前瞻性的， 超出了当前实现真正要求和真正测量的东西 —— 在加入依赖力的成功判据之前，请把那句话当作愿景而非事实。

换句话说：它们是有用的接触密集操作任务，但还不能像上面五个任务那样，被当作支持或反对「力感知有用」的证据。

共用的仿真契约

八个任务共用同一套机器人 / 控制器 / 观测 / 数据契约， 详见仓库的 docs/BENCHMARK_STANDARDIZATION.md 与 docs/PROJECT_GUIDE.md。 策略侧的接口是「一个 PolicyObservation 进，一个 PolicyActionChunk 出」 （15 Hz，世界坐标系下的绝对 TCP 位姿 + 夹爪），见 forcebench/policy_adapters/README.md。
