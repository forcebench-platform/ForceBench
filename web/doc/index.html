Reading task definitions and running the contract tests needs nothing but Python.

1. Overview

ForceBench is a benchmark of eight contact-rich Franka FR3 manipulation tasks in Isaac Lab 6.1 (Isaac Sim 6.0.1), split into five force-classification tasks (the property that decides correct behaviour is visually unobservable — only the interaction wrench carries it) and three contact-dense tasks (gear meshing, nut threading, peg insertion). All tasks share one frozen simulator contract; the runtime refuses to start under any other values:

Physics60 Hz, 64 solver position iterations
Control / policy rate15 Hz (decimation=4)
Arm controllersmooth_position: bounded absolute TCP pose → DLS-IK → rate-limited quintic joint trajectories at 60 Hz
State (7-D)[tcp_x, tcp_y, tcp_z, roll, pitch, yaw, gripper], continuous RPY, gripper −1 closed / +1 open
Action (7-D)absolute target TCP pose + gripper, executed in 50-frame chunks
Force signalraw 6-D wrench [Fx,Fy,Fz,Mx,My,Mz], recorded every frame

2. Installation

Tier A — code reading and contract tests (no GPU, no Isaac Sim)

git clone https://github.com/pkuhanxuan/ForceBench
cd ForceBench
pip install -r requirements-dev.txt        # pytest numpy h5py msgpack websockets opencv-python
python -m pytest tests/
Expected: 102 passed, 5 failed, 2 skipped. The 5 failures are known and documented in KNOWN_ISSUES.md; the 2 skips need a real Isaac Lab environment. Then confirm the task registry: python -c "from forcebench.registry import task_names; print(sorted(task_names()))" should print eight task names.

Tier B — running the simulator (collection, evaluation, replay)

  • Isaac Sim 6.0.1 / Isaac Lab 6.1.14 — the versions official data is collected on. Install Isaac Lab per its official instructions; a conda environment named env_isaacsim6 is the default expected by run_native.sh. (The FORGE factory assets for gear_mesh/nut_thread were historically extracted from an Isaac Lab 2.3.2 container deployment — see NOTICE.md.)
  • An NVIDIA GPU supported by Isaac Sim.
  • Third-party 3D assets in place (Section 4).

All simulator entry points go through run_native.sh, which activates the conda environment, exports the asset directory, and dispatches into Isaac Lab.

3. Environment variables

Defaults point at the original development machine and must be overridden elsewhere, otherwise you get confusing path not found failures. The four roots must be pairwise distinct and outside the code directory (forcebench/paths.py enforces this):

export FORCEBENCH_DATA_ROOT=/your/path/forcebench_data        # formal datasets / eval results
export FORCEBENCH_SCRATCH_ROOT=/your/path/forcebench_scratch  # disposable output
export FORCEBENCH_ARCHIVE_ROOT=/your/path/forcebench_archive  # archives
export FORCEBENCH_ASSET_DIR=/your/path/ForceBench/assets      # assets

export FORCEBENCH_ISAACLAB_ROOT=/your/path/IsaacLab           # used by run_native.sh
export FORCEBENCH_CONDA_SH=/your/path/miniforge/etc/profile.d/conda.sh
export FORCEBENCH_CONDA_ENV=env_isaacsim6

4. Third-party assets

Seven of the eight tasks depend on third-party 3D assets that ForceBench does not redistribute — the repository ships only its own wrapper files, checksums, and instructions. Licences permit our use but not our re-hosting; see NOTICE.md for the authoritative per-task table. In short:

SourceTasksHow to obtain
NVIDIA Omniverse SimReadyweight_sort, rattle_sortDownload from the SimReady catalogue
Lightwheel Kitchen (CC BY-NC 4.0)stove_turn_on, faucet_turnOfficial Lightwheel release; non-commercial use only
NVIDIA Isaac Lab FORGEgear_mesh, nut_threadRun the FORGE deployment of Isaac Lab 2.3.2 and copy its factory assets
ArtVIPradmanso_drawer_sort_tableLicence under review — see NOTICE.md

After collecting the files, verify them against our build:

cd assets && sha256sum -c SHA256SUMS
The robot asset franka_mimic.usd and the peg_insert geometry are provenance-unconfirmed and not distributed; resolving their chain of custody (or switching to the official Isaac Lab Franka asset) is the top v1.0 work item. Until then, Tier B requires obtaining these files from the maintainers. An automated scripts/download_assets.sh is likewise planned but not yet implemented.

5. Generating expert data

Expert collection is dispatched through one entry point; each task runs 32 cloned environments in a single Isaac process and writes one HDF5 file per episode plus a QC report:

# the five parallel-collection tasks
./run_native.sh expert --task weight_sort                --seeds 0-199
./run_native.sh expert --task rattle_sort                --seeds 0-199
./run_native.sh expert --task stove_turn_on              --seeds 0-199
./run_native.sh expert --task radmanso_drawer_sort_table --seeds 0-199
./run_native.sh expert --task peg_insert                 --seeds 0-199
./run_native.sh expert --task faucet_turn                --seeds 0-199

# gear_mesh / nut_thread use privileged FORGE experts; fewer seeds, more workers
./run_native.sh expert --task gear_mesh  --seeds 0-19 --workers 2
./run_native.sh expert --task nut_thread --seeds 0-19 --workers 2

./run_native.sh expert --list      # list registered expert plugins

Episodes land under $FORCEBENCH_DATA_ROOT/datasets/<task>/. Replay any episode to verify determinism:

./run_native.sh replay $FORCEBENCH_DATA_ROOT/datasets/weight_sort/seed_000_episode_01.hdf5

Seed semantics matter: several tasks encode class balance in the seed (e.g. even seeds = light box in weight_sort; each seed pair contains one of each class in rattle_sort). Always collect contiguous ranges, never cherry-pick. Seeds 0–199 are the training range; 200–299 are reserved for evaluation.

6. Evaluating a policy

Policies run as a separate inference server; the benchmark connects over websocket through a policy adapter (openpi_ws, forcevla_ws, forcebench_ws ship with the repo — see policy_interface.md to write your own):

export FORCEBENCH_POLICY_HOST=127.0.0.1
export FORCEBENCH_POLICY_PORT=8002
export FORCEBENCH_POLICY_ADAPTER=openpi_ws
export FORCEBENCH_ENV_SPACING=6.0    # mandatory, see protocol

./scripts/evaluation/evaluate_vectorized_seed_range.sh \
    weight_sort 200 299 auto \
    $FORCEBENCH_DATA_ROOT/evaluations/weight_sort/my_model_spacing6

scripts/evaluation/audit_expert_replay.py audits replay consistency; scripts/evaluation/render_policy_rollout.py renders individual rollouts to video.

7. Evaluation protocol

The machine-readable source of truth is the eval_protocol field of results/leaderboard.json; the human-readable specification is eval_protocol.md. The rules a leaderboard entry must satisfy:

Seedsfixed range 200–299, contiguous, no cherry-picking (seed parity encodes class balance; the seed must never be a model input)
Rollouts100 per task
Env spacing6 m, mandatory. Smaller spacing lets cloned environments appear in each other's cameras (visual crosstalk); results collected without spacing6 are invalid
Action chunk50 frames per inference (FORCEBENCH_EXECUTE_CHUNK)
Step limitsper-task, resolved by scripts/evaluation/resolve_task_max_steps.py

8. Export to LeRobot

Collected HDF5 episodes convert to the LeRobot format for VLA training (π0.5 / ForceVLA / ForceFlow baselines were trained this way):

python convert_hdf5_to_lerobot.py --task weight_sort \
    --src $FORCEBENCH_DATA_ROOT/datasets/weight_sort \
    --repo-id yourname/forcebench_weight_sort

9. Known issues

  • 5 contract tests fail in a bare environment by design — see KNOWN_ISSUES.md. PRs should not increase the failure count.
  • Some run_native.sh entries (collect teleoperation, smoke checks) reference internal tooling not included in this repository.
  • The contact-dense tasks' success predicates do not yet read force signals (v1.0 item).
  • Datasets and baseline checkpoints are unreleased pending paper submission — see the release plan.
